## v3.3:
v3.3 focuses mainly on performance on large instances (many vCPUs, such as the c8in.96xlarge), where earlier versions scaled poorly; smaller instances gain too (a 20-40% higher forwarding ceiling on a c6in.xlarge, the most with small packets). It also adds receive-interface selection (`-I`), configuration files (`-f`), and a set of reliability fixes. Additional static code tests and dynamic tests were added to the test harness, allowing fixing potential bugs. Finally, passes were made at cleaning up the code, and working through suggestions and bug reports from GitHub and elsewhere. Keep the feedback coming!

**Potential monitoring changes to be aware of:** if you parse gwlbtun's log or health output, check these.
- Log line separator: lines now read `<time>: <thread>(<section>,<level>): <message>`. Earlier versions printed `(<section>,<level>) : : <message>`; the second colon was a typo, with no field ever between the two.
- Health JSON: the tunnel thread key `secsSincelastPacket` is renamed `secsSinceLastPacket`, matching the other entries.
- Health text: "packets dropped on write" is now "packets dropped". The per-endpoint `pktsDropped` (and the summary's `totalPktsDropped`) now also count inner packets gwlbtun can't forward: not IPv4 or IPv6, malformed, or shorter than an IPv4 header. A header-only 20-byte IPv4 packet, previously discarded, is now forwarded.
- The per-endpoint `secsSinceLastPacket` (and the text "since last packet") is updated about once a second rather than per packet, so it can read up to a second high. The UDP and tunnel thread counters are updated once per receive batch.
- GENEVE options in log messages (debug output and the flow-cache notice below) read `GWLBe endpoint: vpce-... Attachment ID: 0x... Flow Cookie: 0x...`: the attachment ID and cookie are hex with a `0x` prefix, and the "Status" field appears only when it isn't OK. Inner packet summaries name the protocol (`Prot UDP, src pt ..., dst pt ...`, or `Prot #N` for other protocols).
- The "GWLB flow cookie changed" notice is now "GWLB data changed for an established flow", names the inner flow and the old and new outer addresses and GENEVE options, and is logged for the first change and every 4096th per flow cache.
- A receive buffer smaller than `--rcvbuf` asked for is reported in one `important` line, worded "GENEVE socket receive buffers are N MB, not the M MB requested (--rcvbuf) ...", instead of seven `critical` lines starting "WARNING: Kernel net.core.rmem_max". It is based on the size the kernel applied rather than a read of `/proc/sys/net/core/rmem_max`.
- Failures to send a packet back to GWLB are logged as "Unable to send UDP packet to GWLB: ... (failures so far: N, logging the first and every 4096th)" rather than once per packet.
- Thread messages: a failure to pin a thread reads "Unable to pin tunnel thread N to core C: ..." (or "UDP receiver thread N"), and a thread slow to stop at shutdown is logged at `important` as "... has not yet shut down - waiting more."
- Configuration errors: stricter number parsing (below) gives new error messages, and `config:` or another command-line-only option in a file is reported as "not allowed in a configuration file" rather than as an unknown option.

**Upgrading from v3.2:**
- UDP receiver threads now default to one per receive queue instead of one per vCPU (see below). On instances with more vCPUs than receive queues that means fewer UDP threads. On a c8in.96xlarge that was much faster; instances between 32 and 192 vCPUs weren't tested. To restore v3.2's layout, use `--udpthreads $(nproc)` (or `udpthreads:` in a configuration file).
- Numeric options are validated: a value that v3.2 read as 0, or as its leading digits (`-p 80abc`), now stops gwlbtun at startup with a message saying what's wrong. Numbers must be plain digits (no spaces, `+` or trailing text). `--reserve` takes counts from 0 to 100,000,000 per table, `--tunthreads` 1 to 255 and `--udpthreads` 1 to 1024.
- `-x`, which no longer did anything, is accepted and ignored with a notice in the log; it will be removed later. Use `--logging geneve=debugdetail` for packet hex dumps.
- Log and health output formats changed in places; see the monitoring changes above.

- Configuration files: `-f FILE` reads options from a YAML file whose keys are the long option names (`udpthreads: 8`, `interface: [ens5, ens6]`). Command-line options override the file; for `-I` and `--reserve` they replace the file's list. `--show-config` prints the effective configuration as a file. Every short option now has a long name (`-s` is `--simple`), errors name the offending file and line, and numeric options are validated instead of silently becoming 0. Parsing moved into `GwlbtunConfig.cpp`; libyaml 0.2.5 is vendored in `third_party/libyaml` and compiled in, so no system package is needed.
- `--udpaffinity nearest`, the new default: one UDP thread per receive queue, each pinned to the closest CPU that services no queue (its hyperthread sibling, else a CPU sharing its L3 cache, else its NUMA node), read from the CPU topology in sysfs. Where every CPU services a queue (most sizes up to about 8 vCPUs; see the [ENA queues documentation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ena-queues.html)) the threads stay unpinned. The thread layout is now worked out with the rest of the configuration: `--show-config` shows it, and startup logs it.
- Improvements for large instances. On a c8in.96xlarge (384 vCPUs), together with the thread and interrupt layout in the new guide, lossless forwarding went from about 2.5M pps with v3.2's defaults to about 8M pps (64-byte and 1024-byte packets; peak about 8.8-8.9M pps) with under 1 ms latency. Guide: [README-Large-Instances.md](README-Large-Instances.md).
- Higher forwarding ceiling on small instances. On a c6in.xlarge (4 vCPUs) behind a GWLB, measured against v3.2 in the same session: 452k vs 328k pps with 64-byte packets (1.38x), 409k vs 324k at 512 bytes and 371k vs 307k at 1518 bytes (1.21x); see the README's performance table. No regression measured on a c6gn.xlarge.
  - gwi- writes go through detached tun queues, one writer per 8 UDP threads (and at least one per receive queue), so they skip the kernel's per-packet flow-table update and its per-device spinlock. Each writer keeps a distinct queue index and UDP thread *t* writes through writer *t* mod the writer count, so forwarded traffic (two-arm and NAT setups) spreads over the transmit queues; previously almost all of it left on transmit queue 0.
  - Each tunnel thread waits on its own epoll set (its tun queue and the interface's stop event). With `poll()`, every wait added the thread to the stop event's wait queue and removed it again, and all of an interface's threads share that queue: its lock took about a fifth of the CPU at 14M pps with 128 tunnel threads.
  - Return packets to GWLB set Don't Fragment in the outer IPv4 header, so Linux leaves their IP ID at 0 (RFC 6864) instead of taking each packet's ID from a counter shared by every thread sending to the same GWLB address (3-13% of CPU at 12-14M pps). They were never fragmented: the kernel rejects raw sends larger than the interface MTU.
  - Large-instance guide: when the GWLB is in the appliance's subnet, a host route to it through the subnet's router lets Linux cache the return route (it doesn't for raw `IP_HDRINCL` sends to a directly connected next hop). That removed the tunnel threads' remaining lock contention, and with two network interfaces raised throughput from about 7M to 13M pps.
  - With 64 network queues (set while the instance is stopped) and their interrupts on the interface's NUMA node, the tuned c8in.96xlarge layout peaked at about 13M pps with 3,000 flows. Results depend heavily on the traffic: with ~131,000 flows the peak was about 8.9M pps, and the instance counted none of the loss above that.
  - Unpinned tunnel threads no longer inherit the CPU pin of the UDP thread that created their endpoint (with pinned UDP threads, every tunnel thread used to end up on one CPU).
  - Each tunnel thread returns traffic to GWLB on its own raw socket, with a 16 MB send buffer (new `--sndbuf` option), instead of one shared socket per endpoint.
  - Per-endpoint packet counters are kept per UDP thread, and a UDP thread takes its reference to an endpoint once per receive batch rather than once per packet.
  - UDP receiver threads now default to one per receive queue of each interface, pinned near the queue (`--udpaffinity nearest`; one unpinned thread per core if the queues can't be found), instead of one per core. Most sizes up to about 8 vCPUs have one queue per vCPU, so the count only changes on bigger ones, which usually have fewer queues than vCPUs (a c8in.96xlarge gets 32 instead of 384). Whenever an interface has exactly one UDP thread per queue, thread i's socket is tied to queue i's CPU (`SO_INCOMING_CPU`, Linux 6.2+), so each queue's packets go to its own thread.
- Fixes to support c8in.96xlarge and other large instances:
  - gwlbtun no longer fails at startup on hosts with more than 256 vCPUs. Thread pools are sized to the configured thread count, with no fixed maximum.
  - Tunnel reader threads wait with epoll instead of `select()`, which corrupted memory once a file descriptor reached 1024 (each GWLB endpoint opens two per tunnel thread, so many-core hosts with several endpoints get there quickly). Each wakeup now drains up to 64 queued packets.
  - `--udpthreads`, `--tunthreads` and the affinity lists are validated, and invalid values exit with a clear message.
  - Tunnel threads default to one per core, but at most 255 per tun interface and leaving room on each gwi- device for its writers: each thread is a queue on the multi-queue tun device, and the kernel caps a device at 256 queues, shared by the tunnel threads and gwlbtun's writers (at least one per receive queue). A c8in.96xlarge with 32 receive queues gets 224. Previously the default of one per core made interface creation fail with E2BIG on hosts with more than 255 vCPUs. If `--tunthreads` leaves room for fewer writers than wanted, gwlbtun says so at startup.
- Log messages are never used as printf formats, so packet bytes in debug hex dumps (and interface names or error text) can't inject format directives.
- Health check clients are served on their own short-lived threads (at most 16 at once), from a report the main thread rebuilds at most once a second. A client that keeps its connection open, or never sends a request, no longer delays other health checks (#43); gwlbtun reads the request, answers and closes, within 2 seconds per client. The clock used for flow-cache expiry runs on its own thread. The health port now sets SO_REUSEADDR, so a restart doesn't fail with "Address already in use" while old health check connections are in TIME_WAIT.
- Only one gwlbtun without `-I` can run per network namespace. A second instance exits at startup instead of silently splitting GWLB traffic with the first; separate network namespaces (containers, `ip netns`) are unaffected. Processes using `-I` with different interfaces can run side by side (see below).
- New `-I IFNAME` (`--interface`) option receives GENEVE only on the listed interfaces (repeatable or comma-separated; default all interfaces), so gwlbtun no longer has to listen on a management interface. `-p` now accepts `ADDR:PORT`, `[IPv6]:PORT` or `IFNAME:PORT` to bind the health check the same way.
- Replies to GWLB leave by the interface the endpoint's traffic arrived on, from the address it arrived at. On an instance with two ENIs registered as targets, replies for traffic sent to the second ENI previously left by the first, with the second ENI's address, and were dropped (observed; with source/destination checking on, as is the default).
- Tunnel devices are created with `IFF_TUN_EXCL`, so a second gwlbtun can no longer attach to a device another one owns. That case now logs "Unable to create TUN device ... (IFF_TUN_EXCL): a device with that name already exists - is this the only gwlbtun trying to use it?", and an endpoint whose interfaces can't be set up drops its packets and retries every 5 seconds instead of retrying (and logging) on every packet. With `-I`, device names include a hash of the interface list, so processes serving the same endpoint on different interfaces don't collide.
- Idle endpoint teardown (`-t`) now runs entirely on the reaper thread, and an endpoint is never re-created while its previous interfaces are still being torn down, so CREATE and DESTROY hooks for an endpoint always alternate.
- Setting up a new endpoint (opening its interfaces, starting its threads and running its CREATE hook) no longer holds up the other UDP threads, the reaper or health checks; only the UDP thread that saw the endpoint's first packet does the work, and waits for it. Packets for that endpoint arriving on other UDP threads while it's set up are dropped, since its interfaces aren't ready yet. Previously every UDP thread's first packet for any endpoint waited for it. An idle endpoint whose last reference is released by a packet thread rather than the reaper still blocks re-creation until it's gone.
- gwlbtun raises its open-file soft limit to the hard limit at startup, and logs about how many endpoints fit (each needs about six file descriptors per tunnel thread). Hook scripts get the original soft limit back, and inherit none of gwlbtun's file descriptors: every one is now close-on-exec. Previously a hook that left a process running kept copies of the endpoint's tun queues, so re-creating its interfaces failed, and of the GENEVE sockets and health port, which outlived gwlbtun.
- Running more UDP or tunnel threads than the instance has CPUs is logged as untested (it still runs). `--rcvbuf` accepts 1 to 2047 MB; larger values overflowed.
- The example hook scripts turn off IPv6 router solicitations on the tunnel interfaces. Nothing on a GWLB tunnel answers them, and the kernel's endless retries counted as tunnel activity, so `-t` could fail to time out an idle tunnel. IPv6 traffic through the tunnels is unaffected; custom hook scripts should do the same (see Kernel sysctls in the README).
- Example topologies and hooks: the CloudFormation templates build gwlbtun on AL2023, install it with the systemd unit and a configuration file, default to t2.small, and set up the one-arm topology's dual-stack endpoint with native CloudFormation properties instead of Lambda functions. The two-arm topology is IPv4-only, as its VPCs are. `create-nat.sh` now sends replies back through the endpoint's `gwo-` interface (a connection mark and a routing table per endpoint); before, the un-NATed replies left by the default route and never reached the application.
- Faster shutdown and endpoint teardown: a tun interface's threads wait on its packets and on a stop event together, and destroying the interface wakes them all at once, instead of each thread checking a stop flag on a timer, one interface at a time. Exiting with 20 endpoints took 44 seconds and now takes about 2, nearly all of it the kernel removing the 40 tunnel interfaces (about 50 ms each). At roughly 2 seconds per endpoint, a host with a few dozen endpoints could hit systemd's default 90 second stop timeout and be killed before its DESTROY hooks ran.
- The DESTROY hook now runs while both of the endpoint's interfaces still exist; earlier versions removed the egress (gwo-) interface first. An endpoint whose setup fails part-way (for example on a file descriptor or thread limit) runs neither hook and leaves no interfaces behind, and gwlbtun keeps running and retries it.
- Per-endpoint handler cleanup and simplification: every part of an endpoint (interfaces, threads, sockets, flow caches, hooks) is set up by constructors and taken down by destructors, in an order fixed by the class layout, with no separate stop or teardown step to forget. The same applies to the UDP receiver threads and to the process as a whole.
- A fatal error at startup (for example the health port already in use) is logged and gwlbtun exits with status 1; one that escapes everything else is written to stderr and the log before gwlbtun aborts. A health check client that doesn't finish within 2 seconds is logged with its address, and shutdown no longer waits for such clients.
- Hook scripts are started with the interface names and endpoint ID as separate arguments rather than pasted into a shell command line. Hooks that fail to start, exit non-zero or are killed are now logged.
- Flow-cache keys read the inner ports correctly for IPv4 packets with IP options, IP fragments, and IPv6 packets with extension headers.
- Release builds use `-O3` instead of `-Ofast` (which allows floating-point shortcuts and compiler-introduced data races between threads), and the plain `cmake3 . && make` build now produces an optimized (Release) binary; previously it had no optimization unless `CMAKE_BUILD_TYPE=Release` was passed. User-supplied compiler flags (for example `-DNO_RETURN_TRAFFIC`) are no longer discarded.
- Other fixes: empty UDP datagrams sent to the GENEVE port are dropped before parsing and no longer counted as received packets; queued log messages (including "Shutdown complete.") are printed before exit; `--logging geneve=debugdetail` now shows the GENEVE debug output it was suppressing; flow-cache health reports how many entries the last sweep removed; the flow-cache notice when GWLB's data for a known flow changes now shows what changed (see the monitoring changes above); GENEVE sockets no longer close fd 0 at shutdown; the help text and README give the real default log level (`info`) and describe hook arguments as GWLB endpoint IDs; the README Docker section matches the Dockerfile.

## v3.2:
- Corrected terminology: the GENEVE Option Class 0x0108 type-1 field is the GWLB **endpoint** (VPC endpoint, `vpce-`) identifier, not the ENI of that endpoint. Logs and health output now label it "GWLB endpoint" and show the `vpce-` prefix. **Health JSON change:** the per-ENI object's `eniStr` key is renamed to `gwlbEndpointId` (value now `vpce-`-prefixed) - update any tooling that parses the health JSON.
- Vendored a header-only subset of Boost (1.92) and nlohmann/json into `third_party/`, so the build no longer needs a separate Boost download or install - `cmake3 . && make` is self-contained on a stock Amazon Linux host (#24, #25, thanks @lyoung-confluent).
- recvmmsg() batch receive on the UDP ingress path, configurable SO_RCVBUF, and reduced shutdown latency for higher throughput (#21, thanks @nikvouk-aws).
- Flow cache split into separate TCP/UDP/Other tables, with a configurable TCP idle timeout via `-i TIME` to match the GWLB flow timeout (UDP and Other use a fixed 120-second idle timeout).
- New `--busypoll USEC` option to busy-poll the NIC on the UDP ingress path for lower latency under high packet rates (default off).
- High-scale flow-cache optimizations: a coarse (1-second) idle timer refreshed in place, flow-cache expiry on a dedicated reaper thread off the health path, optional `--reserve` pre-sizing of the per-table caches, and cache-line isolation of the hot per-ENI counters. Measured on the test rig (256 B, single appliance): no-drop throughput on par with the prior split-cache build (~300k pps) with the tightest latency tail of the builds compared (worst case ~1.7 ms under overload vs ~2.9-5.0 ms before), and ~0% loss at/under the no-drop ceiling. Also fixes a latent shutdown-ordering use-after-free (tunnel threads outliving the flow caches they read), which `--reserve` turned from benign into a reliable crash.
- Raised the GWI/GWO tunnel MTU to carry 8500-byte payloads (8500 + 68 B GENEVE + 28 B UDP headers), matching GWLB's maximum.
- IPv4/IPv6 dual-stack health-check listener (works on RHEL 10+, where the previous socket setup failed).
- Container image and Kubernetes DaemonSet manifest (#13, thanks @ahmetayd).
- Reliability and portability hardening: fixed data races flagged by ThreadSanitizer, replaced unaligned reads of on-the-wire fields with well-defined accesses, now compute and report real health status (#34), route SIGTERM cleanly through the shutdown handler, and build with `-Wshadow` in the always-on warning set.
- Fixes: malformed health-check JSON (#26), uninitialized health socket busy-loop (#29), uninitialized outer UDP checksum (#28), Geneve per-option bounds check (#31), socket/write return-value handling (#32), fd cleanup on ENI teardown (#36), compiler warnings (#33), and build hygiene (#24, #25) - thanks @lyoung-confluent.

## Public Development v3.1:
- Performance improvements to /dev/net/tun handling, packet manipulation, and memory usage. The improvements help more on higher CPU core counts - at 4 cores, the improvements result in approximately 4.3% improvement as measured by packets per second, but at 32 cores it's 37.2% more.
- Clean up /dev/net/tun fd handling to reduce file descriptor count
- Improved flow cookie tracker hashing algorithm to reduce collisions in high cps, low entropy scenarios.
- Several bug fixes (rare crash on startup, rare FD leaks on error paths)

## 2022.11.17 Release:
- **Update to support IPv6 payloads from GWLB**
- Updated CMakeLists file to cleanly separate Debug and Release build options
- Rearrange initializers to cleanup some harmless ```-Wreorder``` warnings, and reorder a couple fields to optimize memory access
- Update packet hashing algorithm to be in one place (utils.h, defined inline), along with adding stats as to how the hash algorithm is performing to the status webpage when the debug flag is on. Thusfar in testing, the simple add-all-fields algorithm does well with avoiding collisions and is fast.
- Updated help on script parameters, as suggested by liujunhui74
- Added recognizing the flow in both directions when seen the first time, as suggested by liujunhui74
- Cleaned up debugging output to be consistent, and added milliseconds to the timestamp
- Update shutdown process to have all threads stop processing, then shutdown. In high PPS testing, there would occasionally be a race condition in shutting down that would result in a use-after-free error which this resolves.
- Updated the hashing for PacketHeader classes to extend std::hash instead of providing their own additional classes to std::unordered_map for cleaner operation.
- Reserve 3 GENEVE header options by default when processing a GENEVE packet, avoiding an unnecessary realloc due to dynamic vector expansion.
- Fixed an issue where in high PPS testing, the UDP thread would take a long time to shutdown (due to not checking for the shutdown requested flag in the inner packet processing loop)
- Replaced some ```sprintf```s with ```snprintf```s in ```hexDump()``` for safety
